# ROV 自主导航系统：向 Agent 驱动架构演进的建议

> 项目：基于大语言模型的水下 ROV 智能巡检与自主导航系统  
> 目标：在**目标大致区域已知、精确位置未知**的条件下，让 ROV 自主探索、发现、确认并接近目标。  
> 文档性质：基于当前项目讨论提出的**架构建议与实施计划**，不是对现有代码已实现功能的审计。

## 1. 核心判断：我们是否已经在做 Agent？

**基本上是。** 如果目前系统已经实现“获取外部状态 → 调用 LLM 做决策 → 执行动作 → 根据新反馈再次决策”，它就具备了 Agent 的基本闭环。

因此，**不建议为了使用“Agent”这个名称重构整个项目，也不建议把 LangChain、LangGraph 等框架本身当成目标。** 工程上的重点应从“能够反复调用 LLM”转移到“能够围绕持续任务进行有记忆、可验证、可恢复的自主行动”。

需要确认的不是有没有 LLM，而是：

1. **持续目标**：系统能否一直记住“找到红色目标并完成检查”，而不仅是处理当前一条指令？
2. **可用记忆**：是否知道哪些区域已探索、哪里有疑似目标、此前尝试为什么失败？
3. **自主选择**：看不到目标时，是否能主动选择下一个观察位置，而不是等待人重新指定坐标？
4. **结果评估**：能否判断导航成功、观察失败、目标误检、陷入重复循环，并改变策略？
5. **任务终止**：能否判断任务完成、不可达或资源不足，并给出依据？

**本文建议：把“LLM 参与决策”升级为“Agent 管理任务闭环”，让低层导航保持确定性。**

## 2. 与老师要求的对应关系

老师提出的方向可以转化成一个明确的实验任务：

> 用户指令：“到水池右侧区域寻找红色浮标，确认后接近并检查。”

初始输入中**不提供浮标精确坐标**，仅提供近似搜索区域。ROV 需要：

1. 根据已知地图与当前位置选择观察点；
2. 调用 A* / EGO 等现有导航模块到达观察点；
3. 获取相机图像、检测结果、机器人位姿和执行状态；
4. 把观测写入短期任务记忆或语义地图；
5. 根据是否发现目标、置信度、可达性等决定“继续探索 / 靠近确认 / 换角度观察 / 结束任务”；
6. 在连续失败或重复访问时调整策略，而不是原地反复转圈。

这不是要求 LLM 直接控制推进器，而是**将高层自主性建立在已经存在的感知、规划和控制系统之上**。

## 3. 推荐架构：Agent 决策层 + 可验证工具层

```text
自然语言任务（目标类别/颜色、粗略区域、检查要求）
                    ↓
          Task Manager / Agent
  ┌────────────────────────────────────────┐
  │ 任务状态：SEARCH / VERIFY / APPROACH / │
  │          INSPECT / DONE / FAILED       │
  │ 记忆：已探索区域、目标候选、失败记录     │
  │ 决策：规则门控 + LLM 高层策略选择        │
  └────────────────────────────────────────┘
         ↓ 结构化动作 / 工具调用
  ┌────────────────────────────────────────┐
  │ explore(viewpoint)                     │
  │ observe()                              │
  │ verify_target(candidate_id)            │
  │ approach(candidate_id, standoff)       │
  │ replan() / stop()                      │
  └────────────────────────────────────────┘
         ↓
  A* 全局引导 → EGO 局部规划 → ROS2 tracker → ROV
         ↓
  OceanSim / 传感器 / 视觉检测 / 位姿 / 地图
         ↓
  观测摘要 + 动作执行结果 + 地图更新
         └────────→ 返回 Agent
```

### 分工建议

| 模块 | 职责 | 是否由 LLM 直接执行 |
|---|---|---|
| 视觉前端 | 图像增强、目标检测、类别与颜色判断 | 否 |
| 几何与地图 | 观测射线、可用距离、目标候选位置、已探索区域、占据地图 | 否 |
| Agent / 任务管理 | 保持任务目标，选择下一观察点或是否验证目标 | 可以使用 LLM |
| 安全校验 | 动作白名单、目标区域、障碍与距离限制、超时处理 | 否 |
| 规划与跟踪 | A*、EGO、轨迹跟踪、底层推进器控制 | 否 |
| 执行评估 | 到达/超时/卡住/反复转圈/目标丢失 | 规则与状态估计为主 |

**建议保留现有 LLM + A* + EGO 系统，只在其外侧补上任务状态、记忆、工具接口和评估机制。**

## 4. 相比现在，最需要补充的四项能力

### 4.1 任务状态机：让决策围绕同一个任务推进

建议先使用简单的有限状态机，避免所有流程都交给 LLM 自由发挥。

| 状态 | 含义 | 典型转移条件 |
|---|---|---|
| `SEARCH` | 目标未确认，选择新观察点 | 检测到候选 → `VERIFY` |
| `VERIFY` | 近距离或多帧确认疑似目标 | 确认成功 → `APPROACH`；失败 → `SEARCH` |
| `APPROACH` | 规划到安全观察/检查距离 | 到达并满足条件 → `INSPECT` |
| `INSPECT` | 收集检查所需图像/信息 | 检查完成 → `DONE` |
| `RECOVERY` | 处理导航失败、原地转圈、目标丢失 | 恢复成功 → 原状态；失败过多 → `FAILED` |
| `DONE / FAILED` | 输出任务结果和依据 | 终止 |

状态机负责**边界和安全**，LLM 负责**在允许的选项中做高层策略选择**。例如在 `SEARCH` 状态，LLM 可以比较几个候选观察点，但不能直接下发任意推进器指令。

### 4.2 任务记忆：避免“每次重新思考”

优先做**结构化短期记忆**，无需一开始就上向量数据库。

```json
{
  "task": "find_red_buoy",
  "state": "SEARCH",
  "coarse_region": "pool_right",
  "visited_viewpoints": ["vp_01", "vp_03"],
  "failed_viewpoints": [{"id": "vp_02", "reason": "planner_timeout"}],
  "candidate_targets": [
    {"id": "obj_07", "class": "buoy", "color": "red", "confidence": 0.72, "verified": false}
  ],
  "last_action": "observe",
  "last_result": "candidate_detected"
}
```

上面只是**接口示例**，不是当前系统的真实输出。`confidence` 可以来自视觉模块的检测分数，但不应直接视为物理定位精度或目标真实性概率。

最小实现只需要记录：已访问观察点、候选目标、动作执行结果、最近失败原因、当前任务状态。

### 4.3 工具化动作：让 LLM 只输出受约束的高层意图

不建议开放任意速度、推力和无限循环控制。可以定义少量工具动作，例如：

```json
{
  "action": "explore",
  "viewpoint_id": "vp_04",
  "reason": "unobserved_region_near_target_hint"
}
```

在 ROS2 侧实现工具执行器，校验：

- `action` 是否在白名单中；
- `viewpoint_id` 是否来自已生成、可达的候选列表；
- 是否违反地图、禁入区域、最小障碍距离、深度和时间限制；
- 是否重复执行已失败的操作；
- 执行完成后是否返回标准结果：`SUCCEEDED / FAILED / TIMEOUT / ABORTED`。

特别注意：**LLM 不必负责生成精确轨迹**；它选的是“去哪个观察点”或“采用什么搜索策略”。具体路径仍由 A* + EGO 计算。

### 4.4 行动评估与恢复：让失败能驱动下一次决策

你此前提到 ROV 偶尔在一处转圈。应将它同时视为**导航工程问题**和**Agent 恢复能力的测试场景**。

推荐监控：

- 规划目标距离在一定时间内是否持续下降；
- 机器人是否持续转向却几乎没有有效位移；
- 相同局部轨迹或观察点是否反复出现；
- 规划器是否反复失败、目标是否超时不可达。

出现异常时，先由**确定性的安全/恢复逻辑**暂停当前动作，再由 Agent 在受约束候选中选择“换观察点、重新规划、暂时回退或报告失败”。不能只依赖 LLM 文本判断“我好像卡住了”。

## 5. “自主探索”应该如何落地？

建议先把整个问题简化成 **Object-Goal Navigation（目标导向导航）**，暂不追求完整 SLAM、复杂长期记忆和开放世界推理同时完成。

### 第一版：候选观察点 + 语义记忆

**输入：** 目标类别、颜色、粗略区域、占据地图、当前位姿、相机检测摘要。  
**输出：** 下一个观察点或“确认/接近目标”动作。

实现思路：

1. 从粗略搜索区域内生成有限数量的候选观察点；
2. 过滤碰撞、不允许到达或已明确失败的位置；
3. 为每个点提供可解释信息：距离、已观测程度、预期可见区域、最近失败次数；
4. Agent 在候选点之间选择，而不是自由生成三维坐标；
5. 到达后拍摄、检测、更新探索记录；
6. 发现红色目标后进入验证与接近流程。

实际部署时，探索未知空间应确保**观察点在当前已知可通行区域内**，让相机从安全位置观察未知区域，而不是直接把未知区域当作可通行空间。

### 第二版：引入更合理的探索策略

当第一版能闭环运行后，可以引入 Frontier-based Exploration 或 Next-Best-View 思路，为候选观察点建立评分：

\[
S(v)=w_1 I(v)-w_2 C_{\text{travel}}(v)-w_3 R(v)-w_4 P_{\text{repeat}}(v)
\]

这里：
- \(I(v)\)：预计增加的可观测信息；
- \(C_{\text{travel}}(v)\)：移动成本；
- \(R(v)\)：碰撞或导航风险；
- \(P_{\text{repeat}}(v)\)：重复访问惩罚。

这只是**可选的启发式设计**，不是已验证的最优公式。可以先用规则评分作基线，再比较 LLM Agent 是否确实改善表现。

## 6. 三篇水下视觉论文如何融入，不应与 Agent 混为一谈

三篇论文提供的是**感知前端的准确性**，并不自动赋予系统 Agent 能力。

| 文献方向 | 可以借鉴的内容 | 当前阶段建议 |
|---|---|---|
| Shortis (2015)：水下相机标定 | 校正折射相关的像素—观测射线关系 | 先完成可复现的水下标定或仿真标定测试；无需先实现复杂虚拟中心模型 |
| Revised Underwater Image Formation Model (2018) | 区分直接信号衰减与后向散射 | 理解不同水质、距离下颜色偏移的成因；用于设计实验条件 |
| Sea-Thru (2019) | 借助场景距离图进行后向散射去除和颜色恢复 | 优先在 OceanSim 利用模拟深度图做离线验证；单波束 Ping 测距不能直接等价于逐像素距离图 |

**建议的最小视觉实验：** 原始图像 vs 白平衡 vs CLAHE；除了主观视觉效果，记录目标检测的召回率、误检数量、颜色识别准确率和处理延迟。若仿真深度可靠，再加入距离相关恢复作为扩展组。

需要注意，图像“看起来更自然”不等于后续 YOLO 检测一定更准确，必须用实际任务指标验证。

## 8. 如何证明“Agent 驱动”确实有效？

**建议把实验任务和评价指标提前固定**，避免最后只展示 LLM 输出了一段合理文字。

| 对比方案 | 说明 |
|---|---|
| Baseline A | 已知精确目标坐标，传统 A* + EGO 导航（主要作为导航能力参考） |
| Baseline B | 目标位置未知，按照固定顺序或规则选择观察点 |
| Proposed | 目标位置未知，使用带记忆与反馈的 LLM Agent 选择高层动作 |

重点比较 B 和 Proposed，因为它们面对相同的**不确定目标位置**任务；A 的任务难度不同，不应直接用成功率宣称 Agent 优于传统导航。

建议记录：

- **任务成功率**：是否找到、确认并接近正确目标；
- **搜索时间与路径长度**：达到任务目标所需时间、行驶距离；
- **重复探索率**：反复访问相同区域的比例；
- **异常恢复率**：导航失败后是否恢复并完成任务；
- **误检导致的错误接近次数**：是否被错误目标误导；
- **LLM 调用次数、延迟和计算开销**：判断部署可行性。

测试时尽可能使用同一组场景、目标位置分布和导航参数，独立记录各方法表现。

## 9. 推荐的实现原则与边界

1. **高层用 Agent，低层用传统算法**：任务与观察点选择交给 Agent；运动控制、碰撞约束、紧急停止不交给 LLM。
2. **事件触发而非每帧询问 LLM**：到达观察点、候选目标出现、导航失败或超时才触发决策。
3. **先结构化记忆，再考虑复杂记忆框架**：JSON/ROS2 状态就足以验证第一版。
4. **工具输出必须可验证**：每项动作都返回执行状态与证据，避免把“LLM 说完成了”当成真的完成。
5. **区分位置、方向和距离**：单目检测只给出像素与观测方向；没有可靠的距离约束时，把目标表示为带不确定性的候选，而不是虚构精确三维坐标。
6. **先让简单搜索任务跑通，再做大而全的 Agent**：本科 FYP 的贡献更需要有边界清晰、能够对照验证的系统。

## 10. 可以在组会上如何概括

> 我们目前已经实现了 LLM 结合外部状态的重复决策，所以系统具有 Agent 的基本闭环。接下来不打算重写导航模块，而是重点补充持续任务状态、探索记忆、结构化工具调用和失败恢复机制。目标是让 ROV 在只知道目标大致区域的情况下，自主选择观察点、导航、获取视觉反馈、更新记忆，再决定下一步如何搜索或接近目标。A* 和 EGO 仍负责具体路径规划与执行，LLM 主要负责高层决策。与此同时，我们会把最近调研的水下标定和图像增强方法用于改善感知输入，并通过对照实验评估其作用。

---

**一句话总结：我们不是从零开始做 Agent，而是把现有的 LLM 决策闭环，完善为一个有任务目标、有探索记忆、有工具约束、能评估行动结果并自主恢复的 ROV 智能体。**
